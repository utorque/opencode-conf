# Bootstrap & Context Files (Phase 0 + Phase 4)

Covers the two phases that touch the project's AI-agent context files: **Phase 0 — Bootstrap**
(run once, before exploration) and **Phase 4 — Context Update** (run after a PASS or on the final
iteration). `AGENTS.md` is the canonical agent context file; `.opencode/context/` is the living
project-context tree, used as a source when it already exists.

---

## Phase 0 — Bootstrap (ownership + safety)

Before anything else:

1. **Ensure the working directories exist**: `docs/` and `docs/_backup/`. Do not fail because a
   fresh project has no `docs/` yet.
2. **Check if `AGENTS.md` exists** at the project root.
   - If it exists: read it and back it up to `docs/_agents_md_backup.md`. Phase 4 appends the
     generated section when markers are absent, or replaces only the marked section.
   - If it does NOT exist: bootstrap one. If your harness has an init command (e.g. opencode's
     `/init`), run it and wait for completion. Otherwise create a minimal AGENTS.md:
     ```markdown
     # {Project Name}

     {One-line description — inferred from README, package.json, or repo name}

     ## Commands
     <!-- Auto-populated by make-docs -->

     ## Project Structure
     <!-- Auto-populated by make-docs -->
     ```
3. **Inspect existing `docs/*.md` ownership** before generating anything. A file is generated by
   this skill only when it contains `<!-- make-docs:generated -->` in its first ~2 KB. Classify:
   - **Generated** — safe to refresh.
   - **Unmarked** — human-written or legacy (pre-3.2 output has no marker). Do not overwrite
     unless `--force`; use `--force` to adopt/back up/regenerate, or leave it alone.
4. **Apply the safety policy**:
   - Default: skip conflicts and report them. Generate the rest.
   - `--force`: copy each conflicting file to
     `docs/_backup/<name>.<UTC timestamp>.md`, then overwrite it.
   - `--dry-run`: let Phase 1 finish (it is read-only), then print the applicable doc set,
     conflicts, and planned backups; write nothing and stop before Phase 2.
5. **Check if `.opencode/context/` exists** at the project root. If it does, note it for Phase 1
   (it is a primary source for project intent, design decisions, and terminology) and Phase 4b.
6. **Note other context files** (`AGENTS.md` aside): `.cursorrules`, `.windsurfrules`,
   `.github/copilot-instructions.md`, `docs/`, `specs/`. Read them for consistency, but do not edit
   them — `AGENTS.md` is the only root context file this skill writes; `.opencode/context/` is
   refreshed only when the project already has it (Step 4b).

A generated doc's required first line (before the title):

```markdown
<!-- make-docs:generated -->
# Architecture
```

## Phase 4 — Context Update

Run this phase **only after verification returns PASS, or on the final iteration**. It wires the
docs into the project's context files using progressive disclosure.

### Step 4a — Generate/Update AGENTS.md

Create or update `AGENTS.md` at the project root. It is the canonical agent context file for
opencode, Cursor, Windsurf, Copilot, Codex, and Roo Code. Use the template in
[`../assets/agents-md.md`](../assets/agents-md.md).

Rules:
- Manage **only** the region between the `BEGIN AUTO-GENERATED DOCS SECTION` and
  `END AUTO-GENERATED DOCS SECTION` markers. **Never** delete or modify human-written content
  outside that region.
- If the markers exist, replace only that section. If no markers exist, append the section at the
  end of the file.
- Keep it **under 120 lines** total.
- Use **progressive disclosure** with "Read when" triggers.
- Reference docs with plain relative Markdown links, e.g.
  `[Architecture](docs/architecture.md)`. Do **not** use `@`-import syntax — it is tool-specific
  and not portable.
- **Only list docs that were actually generated.** Remove N/A and `--skip` rows from the template;
  never link a file that does not exist.
- Fill Project Structure (≤8 lines) and Key Commands (≤6 lines) from the exploration findings
  (top-level dir → purpose; build/test/dev/lint commands from package.json/Makefile/etc.),
  summarize architecture in 2–3 sentences, and list the top ~5 conventions and top ~10 domain terms
  extracted from the generated docs.
- If `.opencode/context/` exists, add a `Context tree` row to the Key Documentation table pointing
  at `.opencode/context/CONTEXT.md`, and treat it as the project's living design intent.

### Step 4b — Refresh `.opencode/context/` (only if it exists)

When the project already has `.opencode/context/`, it is both a **source** for the generated docs
and part of the project's living documentation. Keep it consistent with what the docs now say
(this mirrors the repo-wide context-hygiene done-gate).

1. Read `.opencode/context/CONTEXT.md` and every `topics/*.md` it references via `@` paths.
2. If the generated docs surfaced **architecture**, **public API**, **data-model**, or **domain
   glossary** facts that the context tree does not reflect, update the matching section/file:
   - architecture/module map or design decisions → `CONTEXT.md`
   - data model → create/update `topics/data-model.md`
   - large multi-session feature → create `topics/<feature>.md` and add an `@` ref in `CONTEXT.md`
   - domain terms → `CONTEXT.md` glossary
3. Keep `CONTEXT.md` lean enough to load every session; topic files ~1 page max; lazy-load topics
   via `@` path refs in `CONTEXT.md`; use clickable Markdown links for human navigation.
4. **Do not create `.opencode/context/` when it is absent** — it is opencode-specific and only
   maintained when the project has already adopted it.
5. **Do not invent decisions.** Only record rationale already present in code, docs, or the
   existing context tree; flag unresolved drift in the final summary instead of guessing.
